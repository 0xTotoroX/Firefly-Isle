# 病历完整性修复的发布与验收

## 已实现的行为

患者、治疗线和显式提供的化验值在一个事务内保存；治疗线和已有化验值保留 ID。`labResults` 缺省表示保留，空数组表示明确清空；只有被删除的治疗线才解除症状归属。化验批次替换同样整笔成功或回滚。

`persist_patient_record(expected_owner_id, record, create_request_id?)` 在写入前核对发起账号；模型结果不能提供可信患者/子记录 ID。可选创建 UUID 由新草稿生成并在重试时复用，服务器对同一账号返回已保存的同一病历，不覆盖后来编辑；旧两参数客户端仍可调用。授权码在 `get_shared_patient_record` 内验证并返回白名单字段；匿名用户不能绕过授权码读取基础表，分享目标不可改写，撤销只能设置 `revoked_at`。

`consume_usage` 在数据库串行消费同一用户/请求种类的额度，免费/有效订阅额度与每分钟限制同时生效。LLM/OCR 数据库故障返回 503，额度不足返回 429；上游失败仍计作一次尝试，设置读写不消耗额度。完整用量规则见迁移 `20261002111617_atomic_usage_quota.sql`。

工作台的主题和语言变化保持输入、OCR 待确认文字和保存队列。AI 修改互斥；账号切换丢弃旧结果。统计页只读。字段队列解决单页快速修改，跨标签页/跨设备同时编辑仍按最后一次完整记录保存处理，本轮未加入协同编辑或版本冲突合并。

## 发布顺序与兼容边界

1. 重新确认目标 Supabase 项目、真实迁移历史和备份。不要直接运行未经核对的全量 `db push`；历史环境存在手工 SQL。
2. 在发布窗口应用 `20261002105552_record_integrity_and_sharing.sql`，依赖现有患者、治疗线、化验批次/读数、分享、症状和随访迁移。
3. 应用 `20261002111617_atomic_usage_quota.sql`，依赖 `009_usage_ledger.sql` 和 `010_billing.sql`；与对应 LLM/OCR Functions 一起验收。
4. 继续应用 `20261002151647_donation_payment_integrity.sql`、`20261002161000_data_api_grants.sql`、`20261002161100_record_create_idempotency.sql`。先有 service-role 捐赠 RPC 才发布新 webhook，先有可选第三参数才发布新的工作台客户端；不能在缺少迁移时回退到非幂等初次保存。
   Stripe webhook 必须随仓库 `supabase/config.toml` 部署，仅此函数设置 `verify_jwt = false`，让没有用户 JWT 的 Stripe 请求进入原文签名验证。不得为解决回调而关闭其他函数的鉴权，也不得省略 handler 的 Stripe 签名校验。
5. 分享旧 RPC 被撤销，旧基础表分享访问被关闭；旧客户端的分享需要刷新升级。新客户端依赖新保存 RPC，迁移未应用时明确失败。关闭旧记账 RPC 后，旧网关不能作为安全回退版本；出现故障应暂停 AI 入口或发布修复版，不能恢复无额度校验的写入权限。
6. 用专门测试账号/患者验证登录后的新增、编辑后重载、失败重试、账号隔离、分享匿名访问/撤销，以及真实模型调用的额度反馈；再确认部署验收。支付验证另外使用 provider 测试环境，不能用本地签名 fixture 代替真实回调接入。

安全修复不以重新开放基础表分享或放宽归属校验来回滚。迁移不清空现有患者数据；正式部署需要检查历史重复批次和不合法子记录，遇到异常显式报错，不自动删除。

## 本地验收

`npm run test:database` 使用一次性 `postgres:18-alpine`、`--network none`、内存数据目录和退出清理，不读取生产凭据。真实角色/RLS 验证治疗线关联、身份保持、跨账户拒绝、写入回滚、重复批次、授权码/过期/撤销、额度与两个连接争抢最后一次额度。

React 行为测试使用延迟请求验证连续保存、前次失败、语言/主题切换、切病历、切账号、互斥追问及可信身份。公开 Demo 已在 Chrome 验证两字段连续编辑和只读统计筛选，未写入真实患者数据。设计板独立验证六个章节、390px 无页面横向溢出、表单错误/重试、弹窗 Escape 和焦点返回。

后续 SaaS 验收已补充完整本地 Supabase Auth/PostgREST：19 份迁移实际应用，邮箱与匿名身份隔离、13 表读取、临床读写、首次创建并发/重试、公开分享撤销与 Dashboard RPC 通过；另验证有数据的旧 17 迁移升级保留记录及子 ID。完整证据状态见 [`saas-acceptance.md`](../products/saas-acceptance.md)。这些结果不代表生产部署、真实 LLM/支付接入或原生真机完成。设计板仍待用户选定布局，不构成前端换肤验收。

本地 Edge Runtime 另验：LLM/OCR 的 ES256 用户 JWT 能通过网关，未登录/无效 JWT 被拒绝；billing 未配置返回 `503 BILLING_DISABLED`；Stripe 无 JWT 的坏签名进入 handler 后返回 `400 SignatureError`，有效合成签名的忽略事件返回 200。BYOK 的实际 function 保存/读取/删除、AES-GCM 密文、账号隔离通过，仅使用虚构 Key，未触发模型请求。这些网关/存储证据不能替代真实支付 provider 回调和模型结果验收。

早期完整性修复基线（2026-10-02）：83 个测试文件、513 项测试通过，随后整合自托管准备增至 531 项。本轮新增实现的最终检查见 SaaS 验收记录；不要把早期测试数当作当前 HEAD 的结果。构建仍有既有 `liquid1.min` 大分包提示。
