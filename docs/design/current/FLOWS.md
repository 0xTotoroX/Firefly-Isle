# 原型任务与验收场景

本文件规定要展示的用户任务与可观察结果，不固定卡片、侧栏、分屏等视觉形式。全部使用 FIXTURES.json，日期、患者、治疗与指标均为虚构。

## 场景一：干净首页

用户进入产品，想整理刚拿到的报告。默认只展示开始任务所需的输入/上传入口、必要导航和明确的患者上下文。没有真实内容时不显示模拟统计，不用大量示例问题填满留白。

- 能输入或粘贴文字，也能选择示例报告；上传控件有文字含义。
- 能找到已有病历和历史任务，入口不依赖悬停；无需通过聊天才能访问自己的资料。
- 归属未定时不假装已选患者，可在本轮核对保存前确认。
- 没有未完成任务时不展示空的待办区；有未完成核对时可显示一条继续入口，其位置由方案解释。

验收：首次看到页面能识别主要动作；桌面有留白，手机不依靠缩小文字塞入。首页布局具体方案仍待用户认可。

## 场景二：处理并核对报告

选择 `report-a` 后，原型模拟处理进度，再展示提取草稿。处理提示应说明当前状态，允许取消；不得用固定等待假装真实 OCR 调用。

1. 展示原文与提取字段的对应来源，具体布局由方案决定。
2. 把样例中的错误数值 `38` 修正为原文 `3.8`；保留用户输入，不自动变回初始值。
3. 第二个读数缺少参考范围，保留“报告未提供”；日期、单位与归属必须清楚。
4. 确认患者与报告日期后保存；保存成功之前始终是待确认草稿。

需要能演示的失败分支：

| 分支 | 预期行为 |
| --- | --- |
| 文件不可处理 | 说明原因，允许替换文件或改为文字输入，已有输入不消失 |
| 处理失败 | 可以重试或取消，状态不显示为已完成 |
| 保存失败 | 保留已改为 3.8 的数值与其他草稿，允许重试 |
| 保存中重复点击 | 不产生两份已保存记录，不把禁用状态当作处理完成 |
| 切换主题 | 核对字段与当前步骤保持不变 |
| 改变患者归属 | 保存前明确确认，不将甲的草稿静默写入乙 |

原型在内存模拟这些状态；“重复保存不重复建档”在正式产品中需另由真实服务验收。

## 场景三：确认后的结构化记录

保存成功后，用户可读回同一份记录，并能找到原报告。数值、单位、日期和缺失情况与核对结果一致；“已保存”与“待核对”有明确区别。

- 资料详情可连续阅读；基本信息、治疗阶段、化验保持归属，不把全部内容塞进聊天气泡。
- 查看某项指标时展开趋势与相关读数，参考范围和来源可查；没有范围不作正常/异常判断。
- 能返回首页继续任务，再打开这份模拟记录；重置演示时明确恢复初始样例。
- 分享与导出可以展示拟议入口，但未实现的动作明确说明，不伪造下载成功、公开链接或发送结果。

## 内容与窗口覆盖

先检查 1440px 桌面与 390px 手机；这些是建议评审尺寸，不是强制 CSS 断点。使用长方案名、长备注、多个阶段和缺失参考范围，避免只用空页面证明布局可用。补查较窄窗口和键盘焦点，不要求为本轮材料准备运行产品全量测试。

## 评审记录应回答什么

- 首页哪些内容必须默认可见？移除其他内容后，已有资料是否仍容易找到？
- 上传、核对、确认与读回是否连贯，用户能否判断处理到了哪一步？
- 原文、AI 提取、人工修改和已确认数据是否容易分清？
- 失败后能否继续，长内容和手机操作是否仍清楚？
- 哪些只是模拟，哪些仍待设计，哪些需要后续业务合同或后端能力？

这是一条完整任务的评审，不是三张互不相关的首页效果图。
